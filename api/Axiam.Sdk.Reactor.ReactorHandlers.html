Remarks

ReactorServer takes one ReactorHandler from an event to one answer, which is the right shape for the wire and the wrong shape for the code. A reactor registered for three events opens with a switch (e.Event), and that switch carries two defects.

The first is cheap: a misspelled event name is a valid string, matches no case, and is discovered as an event that never fires. The second is not. It is the default arm, which is almost always written ReactorDecision.Allowed(). That answers on behalf of code that never ran — the defect §22.10 rule 2 forbids the runtime from committing, relocated into user code where the rule does not reach it. An operator who set fail_closed on a registration has it defeated by a default arm in a file they never read.

This class is the declarative form, in the spirit of §11's [AxiamAccess]: attribute the methods, collect them, hand the result to ReactorServer. It is pure sugar (§22.14 rule 1): what Handler() returns is exactly the ReactorHandler ReactorServer already accepts. It opens nothing, verifies nothing, signs nothing, and does not filter a patch (§22.10 rule 3).

Instances are built once at startup and are not thread-safe to mutate; the delegate Handler() returns snapshots its bindings and is safe for concurrent dispatch.

Remarks

Methods are invoked against the instance they were found on, so a class-based reactor keeps its state and its constructor-injected collaborators. Reflection does not define an order for GetMethods(), so methods are bound in event-name order and Events() is reproducible between runs.

Exceptions

ArgumentNullException

sources or an element is null.

ArgumentException

An event name is outside the §22.5 registry (which is also how §22.7's hot-path operations are refused), an event is already bound, or a decorated method's signature is not Task<ReactorDecision>(ReactorEvent, CancellationToken).
