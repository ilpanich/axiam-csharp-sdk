Remarks

Why this class exists. Channel takes an already-open channel, and the caller owns its lifecycle. That is a reasonable division — but until now the §8b requirement travelling with it was a sentence of XML doc: "its connection MUST have been opened over amqps:// with a trusted CA". A doc-comment MUST is a note to whoever reads the doc comment. Someone who builds a RabbitMQ.Client.ConnectionFactory from an amqp:// URI and hands over the channel gets a working reactor, no warning, and signed-but-readable token decisions on the wire.

This class is the enforcing alternative. Build the factory here and §8b holds by construction: the URI is checked, TLS is on with verification at its strict default, and there is no argument anywhere that turns either off. The Kotlin and Java SDKs ship the same helper against their own client library, deliberately — SDKs should not disagree about what a reactor is allowed to connect to.

ReactorServeOptions still accepts any channel: enforcing at construction cannot retroactively constrain a channel someone else opened, and refusing to serve on one whose provenance cannot be inspected would break every legitimate custom setup to catch a mistake this class already prevents.

The layering, once. HMAC signing (§8/§22.2) gives authenticity and replay protection across broker hops, which TLS cannot, because TLS terminates at the broker and the broker re-sends. TLS gives confidentiality, which HMAC cannot. A reactor's reply is an instruction to allow, deny or rewrite a token: it needs both, and neither substitutes for the other. 

ConnectionFactory factory = ReactorConnections.CreateConnectionFactory(
    "amqps://reactor:secret@broker.internal:5671/%2f",
    new X509Certificate2("/etc/axiam/broker-ca.pem"));

await using IConnection connection = await factory.CreateConnectionAsync();
await using IChannel channel = await connection.CreateChannelAsync();

public static ConnectionFactory CreateConnectionFactory(string amqpUri, X509Certificate2? brokerCaCertificate = null, X509Certificate2? clientCertificate = null)

Parameters

amqpUri string

The broker URI. MUST be amqps:// (§8b rules 1 and 5); every other scheme is refused here rather than downgraded, because a fallback that works is a fallback that gets used.

brokerCaCertificate X509Certificate2

The CA that issued a privately-issued broker certificate (§8b rule 2 — the common in-cluster case), or null to verify against the OS trust store only. Supplied as an additional trust anchor via RabbitMQ.Client.SslOption.CertificateValidationCallback; see the remarks on BuildValidationCallback(X509Certificate2) for why a callback is the mechanism and what it is careful not to become.

clientCertificate X509Certificate2

A client certificate with its private key, for mutual TLS toward the broker (§8b rule 3), or null. A certificate without a usable private key is refused: half a client identity cannot authenticate, and connecting anyway would silently drop the mutual half of mutual TLS.

Returns

ConnectionFactory

A factory whose connections verify the broker.

Exceptions

ArgumentException

The URI is not amqps://, is unparseable, or the client certificate carries no private key.

Remarks

An unparseable URI is an error here, not a pass-through. A security check must fail closed on an input it cannot read — the opposite arrangement (skip the check when parsing fails) is a real bug that shipped in a sibling SDK.

There is no loopback exception. §8b rules 1 and 5 carry no host carve-out, and the AXIAM server is TLS-only with no plaintext listener for one to reach.
