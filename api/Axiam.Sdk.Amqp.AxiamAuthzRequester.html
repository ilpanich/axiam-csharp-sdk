The AMQP authorization requester (CONTRACT.md §8, "Signed authorization responses", contract 1.68; audit finding N2). It publishes a signed AuthzRequest on axiam.authz.request with a private, exclusive, broker-named reply_to queue, and accepts an answer only when it verifies as the server's signed response to THAT request.

Remarks

Verify the received bytes, deliver the same bytes (audit C2). The signature is checked over the delivery body with its trailing hmac_signature member cut out — never over a re-serialization, whose string escaping would differ from the server's for a reason that echoes < > & or non-ASCII text — and the decision handed to the caller is decoded from those very canonical bytes.

What a response must satisfy (consumer obligations 1–4): allowed a JSON boolean and tenant_id, nonce and hmac_signature present, with the signature the last member and no duplicate or case-variant keys; HMAC-SHA256 under the subkey of the requester's OWN tenant and the key_version it sent, compared in constant time; and tenant_id, correlation_id and nonce equal to one outstanding request, which is then retired. Anything else is nacked without requeue, logged as a security event without a signature value, and never an allow; the check keeps waiting for the genuine answer until it times out.

Trust boundary. The key is the tenant's own subkey, so a valid signature proves the answer came from a holder of it, not from the server in particular; this is why every requester uses its own exclusive reply queue (see the contract's trust-boundary clause). The requester takes the subkey for key_version 2 from the caller — derive it as §8 describes, from the key the management API returns; it never reads it from a response.

A broker confirm is not evidence that AXIAM decided a request, and a minimal-profile server (AXIAM__AMQP__ENABLED=false) reads no AMQP queue at all: a check then times out. Use REST or gRPC there.

Server version, and no unsigned responses. The AMQP authorization requester requires an AXIAM server of 1.68 or later (contract 1.68). Such a server signs every authorization response with the tenant's AMQP subkey and answers on the requester's private reply_to queue. A server older than 1.68 ignores reply_to and answers, unsigned, only on the shared axiam.authz.response queue, which this requester never reads: against it every check times out. There is no option to accept unsigned responses (CONTRACT 1.69 §8): no AXIAM server sends one to a reply queue, so an unsigned response can only have been published by someone else, and it is discarded and logged. During a rolling upgrade from a pre-1.68 server, use REST or gRPC authorization until every replica runs 1.68 or later.

The discard event. Every response that is discarded (reason malformed, unsigned, signature, tenant or unknown_request) logs one warning on Logger with exactly the members timestamp (RFC 3339 UTC), exchange, routing_key (the requester's own reply queue), tenant_id (the requester's OWN tenant, never the one the response claims) and reason. The body is unauthenticated input: no signature, nonce, correlation id or other body member is ever logged.

Asks the server whether subjectId may perform action on resourceId (optionally narrowed by scope) and waits for the verified answer.
