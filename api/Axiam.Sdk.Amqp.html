AxiamAmqpConsumer

AMQP event consumer: verify-before-handler HMAC gate plus the sdks/CONTRACT.md §8 ack/nack matrix, built on RabbitMQ.Client 7.x's async consumer API with automatic connection/topology recovery enabled (D-11).

StartAsync(string, string, AmqpEventType, string, byte[], Func<byte[], CancellationToken, Task>, ILogger?, TimeSpan?, CancellationToken) NEVER hands an unverified delivery to the caller-supplied handler — Verify(byte[], byte[]) runs first, and the handler call site is structurally unreachable until it returns true. The handler is handed the very bytes the HMAC covered (the delivery body, signature member included), never a re-serialization of them. The remaining outcomes follow the exact §8 decision matrix:

  • Every discard — nack(requeue: false), the handler never invoked — is logged as ONE warning-level security event carrying exactly timestamp, exchange, routing_key, tenant_id (the consumer's OWN configured tenant, never one read from the body) and reason, the first that applies in the order of §8 rule 4: malformed (not one JSON object: the first byte is not {, or it does not parse), unsigned (no hmac_signature member), malformed (a duplicate or folded member, a signature that is not a trailing 64-hex member, or a layout that is not the configured AmqpEventType's — before the HMAC is computed), signature, malformed (the verified bytes do not decode), key_version, stale, replay. The event never contains a signature, a nonce, a key, the body, or any member read from it.
  • Handler returns normally → BasicAckAsync.
  • Handler throws PoisonMessageException (poison message) → BasicNackAsync(requeue: false).
  • Handler throws any other exception (transient/retryable) → BasicNackAsync(requeue: true).

No body escapes the consumer (§8 step 2, contract 1.69): whatever the bytes — empty, not UTF-8, a byte-order mark, deeply nested, truncated, of another type — nothing is thrown out of the delivery loop and the next delivery is handled.

AxiamAuthzRequester

The AMQP authorization requester (CONTRACT.md §8, "Signed authorization responses", contract 1.68; audit finding N2). It publishes a signed AuthzRequest on axiam.authz.request with a private, exclusive, broker-named reply_to queue, and accepts an answer only when it verifies as the server's signed response to THAT request.

Hmac

HMAC-SHA256 verify-before-handler primitive for inbound AMQP messages (sdks/CONTRACT.md §8, D-11).

The signature is checked over the received bytes, never over a re-serialization. The canonical Rust signer (crates/axiam-amqp/src/messages.rs, split_trailing_signature on the verifying side) signs the serde_json compact serialization of the message with hmac_signature absent and then appends ,"hmac_signature":"<hex>" as the LAST member. This class cuts that trailing member out of the delivery body and HMACs the remaining bytes exactly as they arrived, so the result does not depend on how any JSON library in this process would print what it parsed (System.Text.Json escapes & < > ' and non-ASCII text, and writes \u001F where serde_json writes \u001f: a genuine message whose fields hold them failed verification when the body was re-serialized).

What is verified is what the handler reads (audit C2). The consumer hands its handler the very bytes that were verified. To make that equivalence hold, a body is refused unless it is one JSON object with unambiguous keys (no key twice at any depth, no two top-level keys differing only by case, nothing after the closing brace) and ends in the trailing signature member: the one reading of the signed bytes is then the only reading any parser can take.

PoisonMessageException

Poison-message sentinel a consumer-supplied handler throws to signal that the current delivery must be nacked without requeue, rather than the default nack-with-requeue applied to any other handler exception (D-11, sdks/CONTRACT.md §8). Mirrors the Go ErrDrop sentinel / Java ErrDrop exception used by the sibling SDKs.

AmqpEventType

The ONE signed event type an AxiamAmqpConsumer consumes (CONTRACT.md §8 step 2c, "Typed: one configured type", contract 1.69, owner decision D-9). AuthzRequest, AuditEventMessage and AuthzResponse are signed with the same scheme under the same tenant subkey, so a genuine message of one type replayed onto a queue that carries another passes the signature check; only its layout tells it apart. A consumer therefore checks the canonical bytes against its configured type's layout and no other, and refuses every other body as malformed before the HMAC is computed. An application that consumes both types runs two consumers, each typed.
