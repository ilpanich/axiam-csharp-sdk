CONTRACT.md §10.3 rule 2's four-way answer to "is this token usable as presented?" — deliberately NOT reducible to valid/active alone (that is the whole point of §10.3): a caller that only checks the boolean has converted a sender-constrained token back into a bearer token.

public enum TokenStatus

Fields

Bearer = 1

Usable, and carries no cnf at all — an ordinary bearer token.

Inactive = 0

valid/active was false — the signature, expiry or tenant check failed, or this token belongs to a different tenant (§10.3 rule 6). Not an error; the server answered "not a token of yours" or "not usable".

SenderConstrained = 2

Usable, and cnf names at least one confirmation method this client can check against PresentedProofs. Call VerifyPossession before treating it as usable BY THE CALLER, not just usable in the abstract.

Unverifiable = 3

cnf is present but names neither method (including an EMPTY CnfClaim — §10.3 rule 3: proto3 cannot express "absent string", so this is the wire spelling of §10.1 rule 9's "names neither" row). MUST NOT be read as unbound.
