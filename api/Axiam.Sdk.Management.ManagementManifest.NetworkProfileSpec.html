Remarks

Judged on the read. The profile read is the effective one, so SessionTimeoutSecs is compared with the value lowered to the tenant's cap: a profile whose stored timeout is above a lowered cap reads as the cap, and a manifest stating the cap is NoChange. A manifest that states a value above the cap differs from the read, so PlanAsync shows an Update; ApplyAsync then sends the replace, the server refuses it (403 authorization_denied, the write gate's H3), and that is the action's failure: reported as the server gave it, ApplyAsync stops, nothing is retried, adjusted or lowered by the SDK (§27.6.2 item 3).

A stated Null is "none": the member is left out of the body.
