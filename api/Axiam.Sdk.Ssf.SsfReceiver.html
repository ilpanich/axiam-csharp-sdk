Remarks

A relying party's tool, not the §27 ssf management namespace (which registers streams). Built over an AxiamClient for its transport: the JWKS, the SSF configuration document and the poll endpoint are fetched under the client's §6 TLS policy, on a session-free transport — no cookie, no session bearer, no redirect.

Keys come only from the configured JWKS (directly, or from a discovery document whose issuer matches): a jwk or x5c header member is never honoured. On an unknown kid the JWKS is fetched again once, and forced refetches happen at most once a minute. A JWKS that cannot be fetched is a NetworkError — not a verdict on the SET.

The key cache expires JwksCacheTtl after the fetch that filled it, and never later than 10 minutes (CONTRACT.md §34.2 P6; a longer setting is clamped for this receiver and reported as a ConfigClampedEvent). A failed fetch — a cold fill, the refresh of an expired cache, or an unknown-kid refetch — counts toward the once-a-minute limit: a SET inside the minute after one makes no fetch and is a NetworkError (no verdict). A successful fill or refresh does not count, so an unknown kid right after one is refetched.

Remarks

Ack and SetErrs are sent exactly as given, and only the members you set. Nothing is acknowledged on your behalf: acknowledge, on the next call, the jtis you processed, and pass each refused one in SetErrs (FromReason(SetFailureReason)) — except a replayed one, which this receiver accepted earlier: acknowledge that (CONTRACT.md §34.2 P2). A SET you neither acknowledge nor refuse is re-offered — and, having been recorded when it verified, then reads as replayed.

Retried per §16 on a transport failure, 5xx, 408 or 429; never on another 4xx (400 is a ValidationError, 404 a NotFoundError, as on the management surface).

A poll never keeps a jti it does not return (§34.2 P1). A failure that is no verdict on a SET — a JWKS or discovery fetch that fails, a replay store that throws — leaves that SET unjudged, and from then on the batch asks the replay store nothing: every later SET that passes steps 1 – 8 is unjudged too, and one that fails them is refused as usual. An unjudged SET is in neither Events nor Refused, is not recorded, and is listed in Unjudged. Do not acknowledge them; the transmitter offers them again. A poll that returns with SETs unjudged emits an SsfUnjudgedEvent (§19.1), so an outage that raised nothing is still visible. When the failure comes before any SET of the batch was recorded, the poll raises it instead (nothing is recorded either way).

Exceptions

AuthError

No access-token provider is configured — no request is sent.

Remarks

The order: 1 three base64url parts, JSON-object header and payload [malformed]; 2 typ secevent+jwt or application/secevent+jwt, any case [invalid_type]; 3 alg exactly EdDSA [invalid_key]; 4 the kid in the configured JWKS, one refetch on a miss, at most once a minute [invalid_key]; 5 the Ed25519 signature [invalid_key]; 6 iss exactly the configured issuer [invalid_issuer]; 7 aud equal to, or an array containing, the audience [invalid_audience]; 8 no exp, no sub, a non-empty jti, a numeric iat, an object sub_id, exactly one events member [invalid_request]; 9 a jti not seen within the replay window [replayed], recorded only once 1–8 passed.

A SET that verifies has been recorded: verifying it again is replayed. Acknowledge a polled SET once you have processed it.

Exceptions

SetVerificationError

The SET was refused.

NetworkError

The JWKS (or discovery document) could not be fetched, or the IReplayStore could not answer (§34.2 P3, P4): no verdict, no reason code, and the jti is not recorded.
